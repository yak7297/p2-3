# 다듬이 서비스 기획서

## 1. 서비스 개요

- 서비스명: 다듬이
- 한 줄 소개: 상황과 말투에 맞게 문장을 자연스럽게 다듬어 주는 AI 메시지 도우미
- 목적: 정중한 요청, 사과, 문의, 이메일 문장을 작성하기 어려운 사용자가 빠르고 부담 없이 적절한 표현을 만들도록 돕는다.
- 타겟 사용자: 대학생, 취업 준비생, 사회 초년생, 직장인

## 2. 문제와 제공 가치

사용자는 전달할 내용은 알고 있지만 상대방과 상황에 맞는 표현을 고르는 데 어려움을 겪는다. 다듬이는 사용자가 작성한 초안을 유지하면서 목적과 말투에 맞는 자연스러운 문장으로 바꿔 준다.

## 3. 페이지 및 섹션 구성

한 페이지 안에서 상단 메뉴를 이용해 각 섹션으로 이동한다.

1. 홈: 서비스 소개와 AI 작성기 이동 버튼
2. AI 작성기: 문장, 사용 상황, 원하는 말투 입력 및 결과 출력
3. 사용 방법: 입력부터 결과 복사까지의 이용 순서 안내
4. FAQ: 개인정보, 입력 범위, 오류 대응 방법 안내

## 4. 핵심 기능

- 원문 입력
- 사용 상황 선택: 이메일, 부탁, 사과, 문의
- 원하는 말투 선택: 정중하게, 친근하게, 간결하게
- AI가 다듬은 문장 출력
- 생성 결과 복사
- 로딩 및 오류 상태 안내

## 5. AI 기능 설계

### 입력

- 사용자가 작성한 원문
- 문장을 사용할 상황
- 원하는 말투

### 출력

- 원문의 의미를 유지하면서 선택한 상황과 말투에 맞게 다듬은 문장
- 결과는 사용자가 바로 복사할 수 있는 형태로 표시

### 사용자 가치

- 어려운 표현을 고민하는 시간을 줄인다.
- 상대방에게 무례하거나 모호하게 전달될 가능성을 낮춘다.
- 사용자가 작성한 내용의 핵심을 유지한다.

## 6. 실패 처리 기준

- 빈 입력: 요청을 보내지 않고 “다듬을 문장을 입력해 주세요.”를 표시한다.
- 너무 긴 입력: 최대 글자 수를 안내하고 요청을 제한한다.
- API 오류: “AI 요청 중 문제가 발생했습니다. 잠시 후 다시 시도해 주세요.”를 표시한다.
- 응답 지연: 일정 시간이 지나면 “응답이 지연되고 있습니다. 잠시 후 다시 시도해 주세요.”를 표시한다.
- 잘못된 응답: 결과가 없으면 오류 안내를 표시하고 다시 요청할 수 있게 한다.

## 7. 화면 및 반응형 기준

- 데스크톱과 모바일에서 메뉴와 입력 폼이 화면 밖으로 벗어나지 않는다.
- 모바일에서는 입력 폼과 결과 영역을 한 열로 배치한다.
- 버튼과 입력 요소는 터치하기 충분한 크기로 제공한다.
- 최소 데스크톱 1440px, 모바일 390px 화면에서 직접 확인한다.

## 8. 보안 및 운영 기준

- AI API 키는 환경 변수 `GEMINI_API_KEY`로 관리한다.
- 실제 키를 코드, README, GitHub 커밋, 스크린샷에 포함하지 않는다.
- 프론트엔드는 AI API를 직접 호출하지 않고 `/api/rewrite` Python 백엔드를 호출한다.
- 과도한 호출을 줄이기 위해 요청 중에는 실행 버튼을 비활성화한다.

## 9. 테스트 기준

| 구분 | 테스트 입력 | 예상 결과 |
| --- | --- | --- |
| 정상 | 교수님께 과제 제출 연장을 요청하는 문장 | 선택한 말투로 다듬은 결과 표시 |
| 빈 입력 | 아무 문장도 입력하지 않음 | 필수 입력 안내 표시 |
| 긴 입력 | 제한 글자 수를 넘는 문장 | 글자 수 제한 안내 표시 |
| API 오류 | 서버 또는 AI API 오류 | 재시도 안내 표시 |
| 모바일 | 390px 화면 | 메뉴, 폼, 결과 영역 정상 표시 |

## 10. 응답 속도·비용·쿼터 운영 계획

현재 프론트엔드는 30초 후 요청을 취소하고, 백엔드는 Gemini 연결을 25초로 제한한다. 기본 모델은 비교적 가벼운 `gemini-3.1-flash-lite`이며 출력도 최대 500토큰으로 제한한다. 요청 중 버튼을 비활성화해 한 사용자의 중복 호출도 막는다.

| 개선 방법 | 적용 계획 | 속도·비용·쿼터 영향 |
| --- | --- | --- |
| 캐싱 | 입력문·상황·말투를 정규화한 뒤 해시 키로 만들고, 외부 KV 저장소에 결과를 짧은 TTL로 저장한다. 원문은 캐시 키나 로그에 남기지 않는다. | 같은 요청의 AI 호출을 생략해 응답 시간과 비용을 줄이지만, 개인정보 및 오래된 결과 문제 때문에 기본값은 비활성화하고 필요할 때만 적용한다. |
| 모델 경량화 | 일반 문장 교정은 현재 Flash Lite 모델을 사용하고, 품질 요구가 높은 기능만 상위 모델로 분리한다. | 경량 모델은 빠르고 저렴하지만 복잡한 문장의 품질이 낮아질 수 있으므로 테스트 결과를 기준으로 선택한다. |
| 입력·출력 제한 | 입력은 1,000자, 출력은 500토큰으로 유지하고 불필요한 프롬프트 문구를 줄인다. | 처리 시간과 토큰 사용량, 요청당 비용을 함께 제한한다. |
| 동시성·쿼터 관리 | 향후 사용자/IP별 분당 호출 제한과 프로젝트 전체 호출 상한을 외부 KV 기반으로 적용한다. `429` 응답에는 재시도 시점을 안내하고 자동 무한 재시도는 하지 않는다. | 순간적인 과다 호출과 예상치 못한 과금을 막는다. 제한을 너무 낮추면 정상 사용자도 기다릴 수 있다. |
| 비동기 큐 | 현재처럼 즉시 결과가 필요한 문장 교정은 동기 응답을 유지한다. 여러 문장을 한꺼번에 처리하는 기능이 추가될 때만 작업 큐와 상태 조회 API를 사용한다. | 트래픽 급증을 평탄화하지만 호출 횟수 자체를 줄이지는 않으며, 큐 운영 비용과 구현 복잡도가 추가된다. |

운영 시에는 평균·95백분위 응답시간, `429`/`5xx` 비율, 모델별 요청 수와 토큰 사용량을 관찰한다. 지연이나 쿼터 오류가 증가하면 먼저 입력·출력 제한과 호출 제한을 조정하고, 그다음 캐시 또는 모델 변경을 검토한다.

## 11. 프론트·백엔드 확장 설계

현재 규모에서는 `js/app.js`와 `api/rewrite.py`의 단순한 구조가 이해하기 쉽다. 기능이 늘어나면 다음 범위로 나누어 변경한다.

| 확장 대상 | 변경 범위와 구조 |
| --- | --- |
| 프론트 모듈화 | `js/app.js`를 `api-client.js`(요청·타임아웃), `form-controller.js`(입력·검증), `result-view.js`(결과·오류 표시)로 분리한다. HTML의 요소 ID와 API 응답 형식은 유지해 화면 변경의 영향을 줄인다. |
| 백엔드 모듈화 | HTTP 요청 처리는 `api/v1/rewrite.py`, 입력 검증은 `services/validation.py`, 프롬프트 구성은 `services/rewrite_service.py`, Gemini 호출은 `providers/gemini.py`로 분리한다. 모델 교체 시 provider 모듈만 변경한다. |
| API 버전화 | 현재 `/api/rewrite`를 유지하면서 새 기능은 `/api/v1/rewrite`로 제공한다. 응답 필드가 호환되지 않게 바뀔 때만 `/api/v2/`를 만들고 기존 버전의 종료 일정을 문서화한다. |
| 수평 확장 | Vercel Function은 상태를 파일이나 메모리에 저장하지 않는 무상태 방식으로 유지해 요청별 인스턴스가 늘어나도 동작하게 한다. 공유 상태가 필요하면 Vercel KV 같은 외부 저장소를 사용한다. |
| 비동기 처리 | 다중 문장·파일 처리 기능은 `POST /api/v1/jobs`로 작업 ID를 만들고 큐가 처리한 뒤 `GET /api/v1/jobs/{id}`로 상태와 결과를 조회하도록 설계한다. 현재의 단일 문장 기능은 빠른 UX를 위해 동기 방식을 유지한다. |

이 구조에서는 새 말투·상황 추가는 프론트 선택지와 검증 상수만 변경하고, 새 AI 공급자 추가는 provider 모듈과 환경 변수만 추가한다. 데이터 저장 기능을 도입할 때는 개인정보 보관 기간과 삭제 기능을 먼저 정의한다.

## 12. API 키 유출 대응 및 재발 방지

키가 코드, 커밋, 로그 또는 스크린샷에 노출됐거나 노출이 의심되면 다음 순서로 즉시 대응한다.

1. Google AI Studio에서 기존 키를 즉시 폐기한다. 파일에서 키를 지우는 것만으로는 이미 복사된 키를 막을 수 없다.
2. 새 키를 발급하고 로컬 `.env.local`과 Vercel의 Production·Preview 환경 변수를 교체한다.
3. Vercel을 재배포한 뒤 AI 호출이 새 키로 성공하는지 확인한다.
4. GitHub 코드 검색, `git grep`, `git log -p`로 현재 파일과 커밋 이력을 검사한다. 이력에 실제 키가 있으면 폐기된 키임을 확인한 뒤 `git filter-repo` 또는 BFG로 제거하고, 협업자에게 알린 후 정리된 이력을 강제 푸시한다.
5. Gemini 사용량과 결제 내역을 확인해 비정상 호출이 있으면 사용 제한을 걸고 기록한다.

재발 방지를 위해 `.env.local`과 실제 키 파일을 `.gitignore`에 유지하고 `.env.example`에는 가짜 예시만 둔다. GitHub Secret Scanning·Push Protection을 활성화하고, 향후 CI에서 Gitleaks 같은 비밀정보 스캐너를 실행해 검사를 통과한 커밋만 배포한다. PR 검토 시 환경 변수·로그·스크린샷에 키가 없는지도 확인한다.

## 13. 프레임워크 도입 검토

현재 과제는 React/Vue 등의 프레임워크 사용을 금지하므로 바닐라 HTML/CSS/JavaScript를 유지한다. 제약이 없는 후속 버전에서 화면과 상태가 복잡해질 경우에만 React 도입을 검토한다.

| 구분 | 내용 |
| --- | --- |
| 장점 | 반복 UI를 컴포넌트로 재사용하기 쉽고, 여러 화면의 상태 관리와 자동 테스트 생태계를 활용할 수 있다. |
| 단점 | 빌드 과정과 패키지 관리가 추가되고 초기 다운로드 용량과 학습 복잡도가 커진다. 현재 규모에는 과도할 수 있으며 이번 과제 제약에도 어긋난다. |
| 프론트 변경 | `index.html`에는 앱 마운트 요소를 두고, `js/app.js`는 `src/main.jsx`와 `src/components/`의 폼·결과·내비게이션 컴포넌트로 교체한다. CSS는 그대로 재사용하거나 컴포넌트 단위로 분리한다. |
| 빌드·배포 변경 | `package.json`, Vite 설정과 빌드 명령을 추가하고 Vercel 출력 디렉터리를 `dist`로 설정한다. `vercel.json`의 프레임워크 설정도 Vite/React 기준으로 바꾼다. |
| 백엔드 영향 | Python `api/`와 Gemini 환경 변수는 유지할 수 있다. 프론트의 호출 주소와 JSON 계약을 유지하면 백엔드 변경을 최소화할 수 있다. |
